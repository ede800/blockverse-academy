Des îles qui ne se parlent pas

Chaque blockchain est un système fermé : Bitcoin ne sait rien de ce qui se passe sur Ethereum, et Ethereum ne sait rien du monde extérieur. Or les utilisateurs veulent déplacer leurs actifs entre chaînes et les smart contracts ont besoin de données réelles (prix, résultats sportifs, météo…). Deux familles d'outils répondent à ce besoin : les bridges et les oracles.

Les bridges : passer d'une chaîne à l'autre

Un token ne peut pas réellement « voyager » d'une blockchain à une autre. Le mécanisme le plus courant est le lock & mint :

  1. Tu déposes 1 ETH dans un contrat-coffre du bridge sur la chaîne A, où il est verrouillé.
  2. Le bridge constate le dépôt et crée (mint) 1 token « wrapped » équivalent sur la chaîne B.
  3. Pour revenir, tu brûles le token wrapped sur B, et le coffre te rend l'ETH sur A.

Autres modèles

  • Burn & mint natif : l'émetteur du token le brûle sur une chaîne et le recrée sur l'autre (ex. le protocole CCTP de Circle pour USDC). Pas de coffre à pirater, mais il faut faire confiance à l'émetteur.
  • Pools de liquidité : le bridge possède des réserves sur chaque chaîne et te paie sur la chaîne d'arrivée (rapide, mais limité par la liquidité).
  • Intents : tu exprimes ton souhait (« je veux 1 ETH sur Base ») et des « solveurs » se font concurrence pour te le livrer rapidement, puis se font rembourser.

Qui vérifie ? Le vrai sujet des bridges

La question décisive : comment la chaîne B sait-elle que le dépôt a bien eu lieu sur A ?

Historique

Les bridges figurent parmi les plus gros piratages de l'histoire crypto : Ronin (~620 M$, 2022, 5 clés sur 9 compromises), Wormhole (~320 M$, 2022, faille de vérification de signature), Nomad (~190 M$, 2022, bug d'initialisation). Un coffre qui contient des centaines de millions est une cible évidente.

La messagerie cross-chain

Au-delà des tokens, on peut transmettre des messages arbitraires d'une chaîne à l'autre : voter sur une chaîne et exécuter le résultat sur une autre, gérer une position DeFi multi-chaînes… Exemples : IBC dans l'écosystème Cosmos (basé sur des light clients), LayerZero, Chainlink CCIP, Wormhole, Hyperlane. Côté Ethereum, les L2 travaillent à une interopérabilité native entre rollups pour réduire la fragmentation.

Les oracles : brancher la blockchain sur le monde

Un smart contract ne peut pas faire de requête web : tous les nœuds doivent obtenir exactement le même résultat, or une page web peut changer d'une seconde à l'autre. Un oracle est un service qui écrit des données externes sur la blockchain pour que les contrats puissent les lire.

  • Prix : indispensables aux protocoles de prêt (liquidations) et aux dérivés.
  • Aléatoire vérifiable (VRF) : tirages au sort équitables pour des jeux ou des NFT.
  • Événements réels : résultats d'élections ou de matchs (marchés de prédiction), météo (assurance paramétrique).
  • Preuves de réserves : vérifier qu'un stablecoin ou un token wrapped est bien couvert.

Le « problème de l'oracle »

Une blockchain peut être parfaitement décentralisée, si son oracle est une source unique, tout le système dépend de cette source. Les bonnes pratiques :

  • Agréger plusieurs sources et plusieurs opérateurs indépendants (Chainlink, Pyth, Redstone…).
  • Utiliser des moyennes pondérées dans le temps (TWAP) plutôt qu'un prix instantané.
  • Ne jamais utiliser comme oracle le prix spot d'une petite pool de DEX : un attaquant avec un flash loan peut le manipuler le temps d'une transaction.
Exemple d'attaque

① Emprunter 50 M$ en flash loan. ② Les utiliser pour faire monter artificiellement le prix d'un token dans une pool peu liquide. ③ Un protocole de prêt qui lit ce prix accepte ce token surévalué comme garantie. ④ Emprunter le maximum, rembourser le flash loan, et partir avec la différence. Tout ça en une seule transaction.
