Un contrat… qui n'en est pas vraiment un

Un smart contract est un programme stocké sur une blockchain, qui s'exécute automatiquement quand on l'appelle, selon des règles fixées à l'avance. Le terme a été inventé par Nick Szabo dans les années 1990, bien avant les blockchains. Ce n'est pas un contrat juridique : c'est du code, et « le code fait loi » — y compris quand il contient un bug.

Analogie : le distributeur automatique

Tu insères 2 €, tu appuies sur B4, la machine te donne une canette. Pas besoin de vendeur ni de confiance : les règles sont gravées dans la machine. Un smart contract est un distributeur automatique numérique, ouvert 24h/24, que tout le monde peut inspecter.

Ce qui les rend spéciaux

ImmuablesUne fois déployé, le code ne peut pas être modifié (sauf s'il a été prévu « upgradable »).
TransparentsLe code et l'état sont publics et vérifiables par tous.
Sans permissionN'importe qui peut les appeler, sans compte ni autorisation.
ComposablesUn contrat peut en appeler un autre : ce sont des « Lego financiers ».
AtomiquesUne transaction réussit entièrement ou échoue entièrement (revert).

Lire un contrat Solidity

Solidity est le langage le plus utilisé sur les chaînes EVM (on trouve aussi Vyper, et Rust ou Move sur d'autres chaînes). Voici une cagnotte : chacun peut déposer, le propriétaire retire si l'objectif est atteint, sinon chacun peut se faire rembourser.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Cagnotte {
    address public owner;                       // qui a créé la cagnotte
    uint256 public constant GOAL = 10 ether;     // objectif
    uint256 public total;
    bool    public closed;
    mapping(address => uint256) public deposits;

    event Depot(address donateur, uint256 montant);
    event Retrait(address owner, uint256 montant);

    constructor() { owner = msg.sender; }

    function deposer() external payable {
        require(!closed, "Cagnotte cloturee");
        require(msg.value > 0, "Montant nul");
        deposits[msg.sender] += msg.value;
        total += msg.value;
        emit Depot(msg.sender, msg.value);
    }

    function retirer() external {
        require(msg.sender == owner, "Pas le proprietaire");
        require(total >= GOAL, "Objectif non atteint");
        require(!closed, "Deja retire");
        closed = true;                              // on modifie l'état AVANT d'envoyer
        (bool ok, ) = owner.call{value: total}("");
        require(ok);
        emit Retrait(owner, total);
    }

    function rembourser() external {
        require(!closed, "Cagnotte cloturee");
        uint256 v = deposits[msg.sender];
        require(v > 0, "Rien a rembourser");
        deposits[msg.sender] = 0;                   // protège contre la réentrance
        total -= v;
        (bool ok, ) = msg.sender.call{value: v}("");
        require(ok);
    }
}
  • msg.sender : l'adresse qui appelle la fonction. msg.value : l'ETH envoyé avec l'appel.
  • require(condition, "message") : si la condition est fausse, tout est annulé (revert).
  • event / emit : journaux que les applications peuvent écouter (historique, notifications).
  • mapping : un dictionnaire adresse → montant, stocké sur la blockchain.
Démo · Interagis avec la cagnotte (simulation)

Essaie : Bob tente de retirer (revert), Alice retire avant l'objectif (revert), puis faites atteindre 10 ETH. Note qu'une transaction qui échoue coûte quand même du gas.

Cycle de vie d'un contrat

  1. Écrire le code (Solidity) et le tester localement (Foundry, Hardhat).
  2. Compiler en bytecode EVM + une ABI (la « notice » qui décrit ses fonctions).
  3. Déployer : une transaction spéciale crée le contrat à une nouvelle adresse.
  4. Vérifier le code source sur un explorateur (Etherscan…) pour que chacun puisse le lire.
  5. Appeler : les fonctions de lecture (view) sont gratuites ; celles qui modifient l'état nécessitent une transaction payante.

Limites et risques

  • Bugs irréversibles : en 2016, une faille de réentrance dans « The DAO » a permis de siphonner environ 3,6 millions d'ETH, provoquant le hard fork Ethereum / Ethereum Classic.
  • Upgradabilité : beaucoup de contrats passent par un proxy modifiable par une équipe. Pratique pour corriger, mais cela réintroduit de la confiance.
  • Pas d'accès au monde extérieur : un contrat ne connaît ni la météo ni le cours de l'euro ; il lui faut un oracle (module 13).
  • Coût : chaque octet stocké et chaque opération se paient en gas.
Bonnes pratiques

Pattern checks-effects-interactions (vérifier, modifier l'état, puis seulement envoyer des fonds), bibliothèques auditées (OpenZeppelin), tests exhaustifs, audits externes et programmes de bug bounty.

Ce qu'on construit avec

Tokens (module 9), échanges décentralisés et prêts (module 11), DAO (organisations gouvernées par des votes on-chain), NFT (module 10), jeux, assurances paramétriques, identité numérique, tokenisation d'actifs réels (obligations, fonds monétaires)…

Que se passe-t-il quand un require échoue ?

C'est l'atomicité : soit tout réussit, soit rien ne change.

Que représente msg.sender ?

C'est ainsi que le contrat sait qui agit — par exemple pour vérifier que c'est bien le propriétaire.
